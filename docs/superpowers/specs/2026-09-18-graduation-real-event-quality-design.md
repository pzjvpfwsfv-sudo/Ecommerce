# G2-B 真实事件 Java 清洗接入设计

日期：2026-09-18。承接已完成的 G2-A 真实 Kafka 回放。用户要求助手独立判断合理性、控制难度、避免新增内容占用 C 盘。本文为实现前评审设计，不将规划内容写成已交付。

## 1. 方案与范围

采用同一 Maven 工程中的独立 `RealDataQualityJob` 入口和真实事件类型，复用 Java 17、Flink 1.19.2、现有依赖与测试方式。旧 `DataQualityJob`、旧 Topic、旧 SQL 和表保持不变。

不选择给旧作业增加两套格式判断：旧模型强制要求渠道、设备、页面字段，且序列化只保留八字段，直接接真实数据会拒绝合法事件或丢失分析字段。也不另建一套 Java 工程或一次重写所有 SQL。

本轮链路为：

```text
真实回放 Topic -> Java 解析与校验 -> 有限时间去重 -> 事件时间/迟到分流
                                      |                  |
                                      v                  v
                                拒绝/重复 Topic      正常、迟到 Topic
```

本轮交付可测试、可部署和可核对的质量入口。下一轮再接独立 Iceberg 明细、Doris 指标和 API；不在本轮增加前端、RAG、CDC、Schema Registry 或新的服务集群。

## 2. 真实数据契约

- 输入为 G1 的 14 个字段，加 G2-A 的 `replay_schema_version,replay_id,replayed_at`，共 17 个字段；正常输出完整保留，不伪造渠道、设备、人口信息或订单身份。
- 用户、商品、品类 ID 保持字符串。`category_id,category_code,brand,user_session` 允许 null，缺失与空字符串规则和 Python 标准化器一致。
- 价格保留规范的两位定点字符串；校验与计算使用十进制类型，不经 float/double。购买事件价格合计不能直接命名为净收入或财务 GMV。
- 允许的行为为 `view,cart,remove_from_cart,purchase`。未知行为、未知字段、缺字段、重复 JSON 键及不匹配的 schema 版本拒绝，不静默兼容。
- 以现有 Python `normalization.py` 为契约基准，用固定跨语言样例验证 Java 的字段标准、JSON 规范化和 SHA-256 事件 ID 一致，包括 null、Unicode、定点金额和原始行号。不能另创一套相似但不同的 ID。
- 数据集、源文件与原始行号必须有效；本轮只接受已登记的 2019 年 10/11 月来源及对应时间范围。行号使用 long 并验证正值。
- 输入消息设置字节上限，拒绝原因使用固定码。异常原文截断并保存内容摘要，避免将超长内容复制进异常 Topic；不得静默丢弃记录。

## 3. 状态与时间边界

以数据集和稳定 `event_id` 为去重键，处理合法事件后先识别重复，再判断迟到，避免同一重发同时被计为新的迟到问题。去重不使用 `replay_id`，新回放任务不能换一个任务 ID 就绕过去重。

复用已有 Keyed State、处理时间 TTL 和 Checkpoint 思路，首轮单并行度、限量验证。TTL 有效期内抑制已见 ID；期满、无状态新作业或丢失恢复点后可能再次输出，不能声称永久去重。跨任务和超出状态期限的防重复累计，在存储阶段设计与验收。参考 [Flink 1.19 状态 TTL](https://nightlies.apache.org/flink/flink-docs-release-1.19/docs/dev/datastream/fault-tolerance/state/#state-time-to-live-ttl)。

Watermark 根据原始 `event_time` 推进，不根据当前系统日期或 `replayed_at`。历史记录不因为来自 2019 年而自动成为迟到数据。合法但落后于当前 Watermark 的记录进入迟到 Topic，本轮不自动回灌；这类记录仍是有效历史事实，后续入湖方案不能把它们直接丢掉。

恢复作业使用兼容的 Checkpoint，不手工改 offset 或清空状态。主动从头回放历史区间与正常断点续传是不同操作：不得假定老 Watermark 会倒退，独立试验使用新的隔离资源和明确的对账范围。

首轮不一次发送 220 万条，不把时间 TTL 当作硬内存上限。扩大规模前实测状态大小和内存，再决定是否采用 RocksDB；本轮不提前引入大状态调优。

## 4. 隔离与可追溯性

- 原始输入只允许 `real_behavior_events_v1` 命名空间及其验证后缀；输出采用独立的 `real_behavior_clean_v1`、`real_behavior_dlq_v1`、`real_behavior_late_v1` 命名空间。输入输出不得同名，不允许使用旧 `user_behavior_*` 目标。
- 所有 Topic 先显式检查或创建，不能依赖 broker 自动创建；验证使用专属后缀，不删除已有 Topic 重跑。
- 消费组、事务前缀、算子 UID 和 Checkpoint 路径使用 G2-B 独立标识，不能沿用旧作业的状态或事务身份。部署前检查同名实例，避免并行启动互相干扰。
- Kafka Source 保留 topic、partition、offset 与原始内容；拒绝和迟到信封记录坐标、原因、事件/回放 ID（可解析时）、作业版本和观察时间。
- 原始字段保留并不等于输出顺序完全不变；经过 keyBy 和并行算子后，以事件 ID 和字段对账，不承诺跨分区全局顺序。
- 使用 Checkpoint 与 Kafka 事务输出；验收消费者使用 `read_committed`。只说明这一段链路经过测试的交付语义，不扩大为回放器、Flink、Doris、Iceberg 之间的全局事务保证。

## 5. 本机执行边界

遵循根目录 `AGENTS.md`。项目文件、源数据和构建产物留在 D 盘工作区；测试临时目录使用工作树外的 `D:\EcommerceDev\temp`。Docker 数据实际位于 `D:\DockerData\wsl`，不重复迁移，不修改系统用户目录或全局 TEMP。

复用已有 Docker Maven/Java 17 镜像。动态部署前只读核对 Flink、Kafka、MinIO 配置及挂载；只启动本轮必要依赖，不假定之前验收容器的名称、端口和挂载等于默认 Compose 配置。Checkpoint 必须位于持久存储，不能放在容器临时层。

当前 C 盘不足 1 GiB，可能影响 Docker Desktop 自身。非 C 盘存储不能替代系统盘余量检查；若空间条件不满足，先交付代码和离线测试，动态验收明确记录未完成，不擅自删除数据或放宽保护。

## 6. 验收与退出标准

1. 新旧 Java 测试均通过；正常和异常样例覆盖字段、类型、金额、空值、事件 ID、输入大小与 Kafka 坐标。
2. 算子测试验证重复、TTL 到期、历史时间、乱序、迟到及状态恢复。人工异常样例只属于测试夹具，不混入真实业务展示数据。
3. 在隔离 Topic 上使用 1,000 条真实记录运行作业。独立读取已提交输出，按 ID 核对原始字段及三个输出分支；这批已核验的正常源数据应得到 1,000 条正常记录，异常/迟到应为 0，出现差异须排查，不能通过更改预期掩盖。
4. 在明确标记的故障验证范围中重发选定真实事件，验证状态有效期内正常输出不增加；受控暂停并从 Checkpoint 恢复，按输入 offset 和输出 ID 证明没有漏处理。保留失败与恢复证据，不只看 Flink 页面显示 RUNNING。
5. 记录实际依赖、启动命令、输入范围、Checkpoint、输出计数、耗时与资源观察；没有实测的数据保持未验收。完整通过后才开始新的落湖与指标接入。

## 7. 设计自检

- 必要性：现有八字段契约确实不兼容真实数据，不是为了增加技术名词另造作业。
- 范围：只新增真实质量入口，不重写旧 SQL、接口或前端；后续落湖仍可复用原技术栈。
- 真实性：保存原始来源、业务时间、缺失值与稳定 ID，测试注入和真实数据分开。
- 正确性：先规定去重与迟到优先级、跨语言 ID 一致性和 offset 追踪，再写实现。
- 可落地性：复用现有镜像和工程，先限量验收，不承诺当前 16 GB 机器同时运行所有服务。
- 当前状态：仅设计完成；新作业、上述测试和真实动态验收均尚未实施。
