# G5-A 真实行为全样本闭环与容量验收设计

日期：2026-10-08。状态：待用户审阅；本设计不是已完成 220 万条动态验收的声明。

## 1. 毕设目标与成功标准

本阶段先补数据科学与大数据技术专业的主线，再接 G4 知识库/Agent。使用已核验的 REES46 2019 年 10 至 11 月稳定用户样本，沿现有真实链路完成一次 **2,199,938 条**历史事件的受控流式回放、清洗分流、Iceberg 明细落地、Trino 对账、Doris 指标发布、FastAPI 和六个工作台页面的可追溯联动。源文件对应 109,950,743 条真实历史记录，但本项目实际进入湖仓的是 2% 稳定用户样本；答辩中两种数量不能混称。

成功不以“服务都启动”为标准，而以源清单、Kafka 确认、Flink 输出、Iceberg Snapshot、Doris 发布、API 响应和页面证据的身份/数量/窗口相互吻合为标准。性能只报告实测吞吐、延迟、Checkpoint、反压与资源消耗，不预设生产 SLA 或全局 exactly-once。历史事件的 `event_time`、当前回放 `replayed_at`、指标 `calculated_at` 必须分别展示；系统处理是流式的，不声称接入企业当前生产流。Flink 官方对历史重处理与事件时间的区分见[文档](https://nightlies.apache.org/flink/flink-docs-stable/docs/learn-flink/overview/)。

## 2. 已有基础与真实缺口

- [数据准备记录](../../graduation/data-readiness.md)：样本 `data/rees46/oct-nov-users-2pct-verified.jsonl` 共 2,199,938 条、1,045,479,893 字节，SHA-256 为 `18a3202d380c8f6c53ad767ec2043d0717df1d3604d2211639bb0fc4699a5437`，覆盖 61 天。重新运行前核对文件及来源清单，不以文件名代替校验。
- G2-A 已有按速率、限量、Checkpoint 续传的回放器；Kafka 交付语义为 `at_least_once`，不是端到端 exactly-once。G2-B Java DataStream 保留原字段、有限 TTL 去重与 clean/late/DLQ 分流；G2-C Flink SQL 单 writer 落 Iceberg；G2-D 已有不可变 Doris 发布与 API。
- 目前正式行为发布 `behavior-v1-s881836466779140976` 仅对应 1,002 条正确性子集，不能用于跨月深度分析或容量结论。Olist 独立订单域已完成九文件 1,550,922 条源记录的全量动态验收；两源无法按用户、商品或订单 ID 拼接。
- G3 六个业务模块在宿主机临时 FastAPI + 真实 Doris 的浏览器验收已通过，但正式容器内静态挂载/持久身份库的最终演示链路尚未验收。本阶段要让行为页面读取新全样本 run，并补上这一部署验收。
- 当前 G2-C runner 可用新 run ID 生成隔离 Topic 和表；G2-D SQL/刷新/验证仍硬编码 `real_behavior_detail_v1`。所以不能直接把全样本追加到旧表，也不能把隔离表 Snapshot 冒充旧表 Snapshot。

## 3. 方案取舍

1. **推荐：独立全样本 run 和湖表，G2-D 显式绑定来源表。** 保留旧 1,002 条表、Snapshot 与发布不动；新 run 使用 G2-C 已支持的 `real_behavior_detail_v1_<run_id>` 命名，表名中的连字符按现有 runner 替换为下划线。对 G2-D 的 SQL 模板、刷新器、验证器和发布元数据增加受严格校验的 `source_table`，旧发布回填为旧表；新发布保留原 `behavior-v1-s<snapshot>` 规则，若跨表出现 run ID 冲突则失败，不复用。改动较多，但审计、回滚和来源解释最可靠。
2. **不采用：向旧表直接追加全样本。** 旧 1,002 条可能与全样本重叠，现有 Flink writer 没有跨已有 Iceberg 表的永久幂等保证；简单追加可能重复，清除旧数据会破坏历史验收。
3. **不采用：跳过 Kafka/Flink，从 JSONL 直接算出 Doris 结果。** 可快速画图，却绕过实时处理与湖仓主链，无法支撑专业方向和答辩中的故障恢复/延迟追问。

来源表参数只能是固定旧表或由合法 `run_id` 推导出的 `real_behavior_detail_v1_<run_id>`，不能接收任意 SQL 标识符。指标公式和 `behavior-v1` 口径不变，只增加来源表身份；历史 run 仍绑定原 Snapshot/原表，不静默重新计算。`data_scope=stable-user-2pct-full` 只能在源数恰好 2,199,938、完整日期范围和独立对账全部通过后发布。新增 `source_table` 必须贯穿 Doris publication、FastAPI meta、前端证据抽屉和 G4 工具证据；旧记录迁移需按原表补全。

## 4. 执行模式与资源门禁

先只读预检，再依次做新 run 的 1 万、10 万、全样本三个门槛；每次使用不同 run ID/Topic/Checkpoint/隔离湖表，不把前两轮汇总成正式 220 万发布。1 万验证字段与口径，10 万验证恢复、持续处理与资源曲线；只有前两轮通过且容量预测有余量时才执行全样本。速率从已测稳定值逐级提高，不以 `replay.py` 默认 100 条/秒当成最终吞吐承诺。全样本可以暂停和续传，但不得在保留状态失效后无条件从 earliest offset 重提到同一非空表。

本项目的动态运行门禁暂定：C 盘至少 5 GiB 可用供 Docker Desktop/Windows 日志和临时运行，Docker 数据仍在 D 盘；D 盘余量需高于 10 万样本实测增量线性外推的 1.5 倍再加 5 GiB，且至少 20 GiB。该门禁是本机保守停止条件，不是 Docker 官方最低要求。2026-10-08 观测 C 盘约 1 GiB、D 盘约 36.6 GiB，**目前不满足 C 盘门禁**，不得直接跑全链路；先让用户用正常系统方式释放空间或审慎调整运行布局，不擅自删除文件、镜像、卷或迁移凭据。所有新缓存、报告、Checkpoint 与大数据保持在 D 盘，旧数据与 Git 未跟踪文件保留。若预检仍不通过，可先做离线测试/脚本设计，动态验收明确标“未执行”。

每级记录源文件 SHA、run ID、Topic offset、回放确认数、Flink Job ID/Checkpoint、clean/late/DLQ 分原因计数、Iceberg 表/Snapshot、Trino distinct `event_id`、Doris `metric_run_id`、任务耗时与磁盘增量。处理时间 TTL 默认 24 小时，若累计运行超过状态有效期或丢失恢复点，不能声称重放仍可永久去重；重复或缺失门禁失败后暂停并诊断，禁止通过删除旧表/Topic“修好”结果。回放结束后等待 Kafka lag 归零和新 Checkpoint/Snapshot 提交再停止 writer，不把“发送结束”误判成“全部落湖”。

## 5. 正式发布与页面验收

- 全样本入湖门禁：读取清单 2,199,938 条；raw 已确认数与消费位置可解释；`clean + late + DLQ` 与 Kafka 实际输入尝试数对账。无故障基线预期 `DLQ=0`；若发生至少一次投递的重试，`DUPLICATE_EVENT` 必须能与重发坐标一一对应并单列，不计为新增业务事件，其他非法业务 DLQ 必须为 0。Iceberg 总数和不同 `event_id` 都精确为 2,199,938，日期覆盖 2019-10-01 至 2019-11-30。若发现源内重复/异常，先报告原因，不改写真实记录凑数。
- 来源隔离：Trino 在新湖表的正 Snapshot 上计算；G2-D 刷新器接受合法 `source_table`，校验其 Snapshot/行数/身份，再生成候选指标。四张 Doris 指标表与 publication 回读对账通过后才写 `PUBLISHED`。新 run 不覆盖旧 run；API 必须显示 `dataset_id`、`data_scope`、`source_table`、`source_snapshot_id`、`metric_run_id`、窗口、`calculated_at`。
- 生效选择：现有 API 按发布时间读取最新 publication；全样本发布后应优先选择最近的 `stable-user-2pct-full` run，再考虑正确性子集，防止后续小样本验收意外覆盖业务看板。旧 run 仍可按身份追溯，不能以“最新”暗示其是当前全样本。
- 可视化：现有总览、行为漏斗、排行、质量等页面从新发布读取真实 61 天窗口，显示样本范围和“历史回放”标签；Olist 页面仍独立。六模块桌面/手机浏览器流程、日期/粒度筛选、证据抽屉和失败/空态必须动态核验，不填充假数。若某指标不支持用户留存/因果推断，页面不得因为数据量扩大就新增该结论。
- 性能与恢复：记录 10 万和全样本的回放吞吐、Kafka lag、Flink Checkpoint 时长/失败、反压、Iceberg Snapshot 增长、Trino 计算与 Doris 发布耗时、API P95、CPU/内存/磁盘峰值。恢复实验放在隔离的 10 万轮，不为了制造答辩故事破坏正式发布。报告必须区分 1 万/10 万测试与全样本结果。
- 完整演示另验正式 Compose API 静态挂载、持久化身份库、授权访问及容器到 Doris 的真实通信；宿主机临时账号的旧验收不能替代。只在资源允许时启动必需服务，不要求 16 GB 本机同时常驻所有组件和本地大模型。

## 6. 交付范围与后续顺序

G5-A 只为真实行为全样本闭环和最小兼容改动，不新增库存/退款/人口画像、跨源关联、实时 CDC、HA 集群或用户留存新算法。缺少这些原始字段和持续生产源时不得为“功能丰富”虚构。此阶段完成后再进行 G3 工作台部署收尾与可读的“数据来源/运行状态”入口，随后按已写的 G4-A 知识库、G4-B 单 Agent 计划实施。G4-A 的离线解析/页面工作可在磁盘门禁阻断时并行推进，但 G4-B 的正式电商指标分析必须引用已验收的大样本 run；没有真实模型或真实指标时不得记为通过。

校招与答辩的最终证据包包含：数据来源与 SHA、抽样解释、完整架构和字段口径、各阶段对账/性能报告、六至九个可操作页面截图、知识检索/Agent 引用评测、系统局限与可复现演示脚本。GitHub 只备份代码和汇总证据，不上传原始数据、密钥或服务卷。
